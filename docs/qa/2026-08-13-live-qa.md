Manual-quality browser pass over the deployed app, issue #28.

## How it was driven

The recipe in [`docs/QA.md`](../QA.md), unchanged: real Playwright, real timeouts, never
`--virtual-time-budget` / `--dump-dom`.

`scripts/headless-probe.mjs` was used for the smoke check and reproduced the recorded baseline
exactly:

```
goto: domcontentloaded in 848ms
0ms   #root length=126  text="Loading your checkpoints…"
500ms #root length=6317 text="bora.py CHECKPOINT PATH 0 / 13 CHECKPOINTS Photocard shelf → Setting"
title: bora.py    console (0)    problems (0)    RESULT ok — the app mounted
```

The click-through itself was driven from a Node script against the same bundled Playwright rather
than through the Playwright MCP server: MCP tools only register at session start, and this pass ran
in a session without them. The capability is identical (navigate, evaluate, screenshot, console,
CDP a11y tree, `setOffline`, `setInputFiles`, downloads) and nothing landed in `.playwright-mcp/` —
that directory was never created, and no screenshot was written inside the repo except the ones
deliberately committed under `docs/qa/screenshots/`.

State was set up through real user paths only: work the exercises, or import a backup file through
Settings. Nothing was written into IndexedDB behind the app's back.

## Console capture

Zero messages and zero problems on **every** screen, at both widths. `page.on('console')`,
`pageerror`, `requestfailed` and any response ≥ 400 were collected and drained per screen:

```
home (fresh) · locked-URL fallbacks · shelf (empty) · settings (empty) · setup guide ·
celebration m0 · setup revisit · module m1 · exercise expected-output · exercise effort gate ·
module m1 after e1 · exit exercise · celebration m1 · exit revisit · shelf (earned) ·
home (2 passed) · settings export/import/reset · settings import error · pwa metadata · offline ·
all passed · capstone celebration · m7 e1 expected output · a11y checks
        → messages=0 problems=0 on all 24, at 390px and at 1280px
```

A separate sweep walked **every** module, every exercise, every exit checkpoint, both OS variants of
the setup guide and all 13 photocard SVGs (60 navigations): zero console output, zero failed
requests, zero non-2xx responses.

Two exceptions, both honest:

1. **The clipboard rejection (#44)** — the only console output produced anywhere in the pass, and it
   needs a user click plus a refused clipboard permission.
2. **One unexplained `404`** — a single `[error] Failed to load resource: the server responded with a
   status of 404` appeared once, mid-run, with no URL attached (that run had no response listener).
   It did **not** reproduce: 3 fresh profiles × 6 navigations each, plus the 60-navigation sweep, all
   logged zero non-2xx responses. Recorded here rather than filed, because a finding nobody can
   reproduce is not a finding. If it recurs, capture it with `page.on('response')` so the URL is known.

## Checked and deliberately not filed

- **`SCREENSHOT PENDING` on 4 setup steps per OS.** The installer, terminal and editor captures need
  real Windows and macOS machines; the guide states the gap explicitly rather than faking an image.
  Known from #13, not a defect.
- **The celebration field in a full-page screenshot.** `.celebrate-field` is `position: fixed;
  inset: 0`, so a full-page capture taller than the viewport shows the screen underneath it. That is
  a screenshot artefact, not a layout bug — the committed celebration shots are viewport-sized for
  exactly this reason.
- **Cracks are drawn on the shelf card only**, not on the celebration screen's preview of the card
  just earned. That matches the stated ownership in `src/PhotocardShelf.tsx` ("Cracks belong to the
  card") and is a design choice, not a defect.
- **The whitespace toggle's on-state is conveyed by fill colour** (outlined = off, accent-filled =
  on) with the label unchanged. That is the design system's segmented-control idiom, the a11y state
  is exposed correctly (`checkbox [checked]`), and the target is 44px. Left alone.
- **`#35` and `#36`** were fixed before this pass and were not re-checked as findings. The loading
  state is visible in the probe output above (`#root` says "Loading your checkpoints…" at 0 ms), and
  both web-app-capable metas are present.
- **The blank-headless claim** stays retracted; see [`docs/QA.md`](../QA.md). The app mounted on
  every one of ~200 navigations in this pass.

## Not testable from this host

This is a Raspberry Pi running Debian Lite arm64 — no desktop, no system browser beyond headless
Chromium.

- **A real install.** The manifest, icons, metas, scope and service worker are all verified, but
  nothing here can accept an install prompt, so the installed launch (standalone chrome, splash
  screen, home-screen icon rendering, portrait lock) is unverified.
- **Real devices and other engines.** Everything was Chromium at emulated widths. iOS Safari and
  Android Chrome rendering, real touch behaviour, and the iOS-only `apple-` meta path are unverified.
- **The setup guide's installer screenshots** — see above; they need Windows and macOS.
- **Actual Python execution.** The app is trust-based by design (the learner declares the match), and
  the curriculum outputs were verified in a real terminal separately under #11 and #12.
